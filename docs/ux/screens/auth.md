# 인증 (`/login`)

실 검진 데이터를 불러오기 위한 본인 인증. 앱 레벨 규칙은
[ux-design.md](../ux-design.md)에 있고 여기서 반복하지 않는다.

---

## 목적

**JTBD**: 예시가 아니라 **내 검진 결과**를 보고 싶다. 인증은 그 대가고,
지금 뭘 해야 하는지·얼마나 남았는지 알고 싶다.

이 화면의 설계 조건은 하나다: **사용자가 이 앱을 떠나 토스 앱으로 갔다가 돌아온다.**
돌아왔을 때 화면이 무슨 상태인지 즉시 읽혀야 하고, 떠나 있는 동안 시간이 흐른다는 걸
알아야 한다.

대시보드가 "훑기 5초"의 화면이라면 이 화면은 **대기의 화면**이다.
정보를 늘리지 않고 지금 할 일 하나만 크게 말한다.

### 인증은 벽이 아니라 옵트인이다

`/`는 예시 데이터로 그냥 열린다. 이 화면은 대시보드 머리의 링크로만 들어온다.

주 사용자가 평가자(`PRODUCT.md`)인데 첫 화면이 실명·휴대폰·토스 앱을 요구하면
대부분 거기서 멈추고, 그러면 화면을 아무도 못 본다.

### 왜 성별을 여기서 받나

**API 응답에 성별이 없다.** `waist`·`hemoglobin`·`yGPT`는 판정 기준이 성별로 갈리므로
(`남: 13-16.5 / 여: 12-15.5`), 값이 없으면 판정이 **조용히 틀린다.**

신원 확인용이 아니라 **판정에 쓰는 기준**이다. 이름·생년월일도 같은 목적(내 데이터
특정)으로 받으므로 같은 폼에 있어도 성격이 어긋나지 않는다.

---

## 레이아웃과 위계

한 열, `max-w-md`, 세로 가운데. 대시보드의 2열 그리드와 달리 **선택지가 하나뿐인
화면**이라 폭을 넓힐 이유가 없다.

```
┌─ 내 검진 결과 불러오기 ───────────────┐
│  국민건강보험공단 기록을 조회합니다.   │
│  토스 앱 인증이 필요합니다.            │
├───────────────────────────────────────┤
│  이름          [              ]       │
│  생년월일      [ YYYYMMDD     ]       │
│  휴대폰 번호   [ 01012345678  ]       │
│  통신사        [ 선택        ▾ ]      │
│  판정 기준     ( ) 남성  ( ) 여성     │
│                허리둘레·혈색소·감마지티피는
│                기준이 성별로 다릅니다. │
│                                       │
│  [        인증 요청        ]          │
│                                       │
│  입력한 정보는 조회에만 쓰이고         │
│  저장하지 않습니다.                    │
└───────────────────────────────────────┘
```

위계 근거:

1. **제목이 목적을 말한다** — "로그인"이 아니다. 계정을 만드는 게 아니라 기록을 조회한다.
2. **토스 앱이 필요하다는 걸 폼 위에서 미리 알린다.** 다 입력하고 나서 "앱 켜세요"를
   만나면 준비가 안 된 사용자는 4분 30초를 통째로 낭비한다.
3. **저장하지 않는다는 문구는 버튼 아래.** 위에 두면 읽기 전에 누르고, 아래에 두면
   "눌러도 되나" 망설이는 순간에 눈에 들어온다.
4. **되돌아가기는 맨 위, 약하게.** 경로는 열어두되 주된 행동과 경쟁하지 않는다 —
   위치로 찾기 쉽게 하고 무게는 링크로 낮춘다.

   맨 아래에 두었더니 출구가 사라졌다. 폼이 세로로 길어(인증 수단 12개 + 조회 기간 +
   판정 기준) 첫 화면에 걸리지 않고, 검증 에러가 뜨면 더 밀린다. **인증은 벽이 아니라
   옵트인**인데 나가는 문이 안 보이면 벽과 구별되지 않는다. 안 보이는 출구는 없는 출구다.

**폼과 대기는 같은 카드가 내용만 바뀐다.** 화면을 새로 만들지 않는다 — 둘은 하나의
절차이고, 카드가 통째로 바뀌면 사용자는 자기가 어디 있는지 다시 찾아야 한다.

## 상태

여섯 개다. 이 중 셋(**인증 대기·시간 초과·인증 실패**)이 이 화면의 실제 설계 대상이고
나머지는 앱 규약대로다.

| 상태 | 화면 |
| --- | --- |
| **폼 입력** | 위 레이아웃. 검증 에러는 필드 아래 인라인 |
| **1차 요청 중** | 필드 전부 `disabled`, 버튼 라벨 `인증 요청 중…`. **스켈레톤도 스피너도 없다** — 레이아웃이 안 바뀌고 곧 끝나는 전환이라 자리를 지키는 게 맞다. 컨테이너 `aria-busy="true"` |
| **인증 대기** | 카드 내용이 대기 안내로 교체. 남은 시간 + 진행 막대 + 인증 완료 + 취소. 아래 상세 |
| **시간 초과** | 폼으로 복귀. **입력값은 그대로 살아 있다.** 폼 위에 안내 배너 |
| **인증 실패** | 폼으로 복귀. 입력값 살아 있음. 폼 위에 원인 + 다음 행동 |
| **성공** | `/`로 이동. 대시보드가 실 데이터로 그려진다. 중간 축하 화면 없다 |

빈 상태·오프라인·새로고침은 [ux-design.md](../ux-design.md)의 규약대로다.

### 인증 대기 (4분 30초)

```
┌───────────────────────────────────────┐
│  토스 앱에서 인증해 주세요             │
│                                       │
│  토스 앱에 인증 요청을 보냈습니다.     │
│  앱에서 인증을 마친 뒤 아래 버튼을     │
│  눌러 주세요.                          │
│                                       │
│         남은 시간  4분 30초            │
│  [████████████████████░░░░░░░░░░]      │
│                                       │
│  [      인증을 완료했습니다      ]     │
│  [           취소           ]          │
└───────────────────────────────────────┘
```

- **버튼이 2차 요청의 방아쇠다.** 자동 폴링을 하지 않는다 —
  검증된 유일한 출처인 [probe-candiy.sh](../../dashboard/scripts/probe-candiy.sh)가
  사람의 입력을 기다린 뒤 2차를 **한 번** 부른다. 인증 완료 전에 2차를 보내면 어떻게
  되는지(대기 응답인지, 세션 무효화인지) **확인되지 않았다.** 모르는 채로 반복 호출하면
  인증 세션을 스스로 깨뜨릴 수 있고, 그 실패는 "인증했는데 안 된다"로 나타나 원인이
  안 보인다.
- 그래서 **본문이 "버튼을 눌러 주세요"까지 말한다.** 앱에서 돌아온 사용자가 여기서
  멈추는 게 이 흐름의 가장 흔한 실패다.
- **진행 막대는 남은 비율을 그린다**(100% → 0%). 줄어드는 방향이 남은 시간의 방향과
  같아야 한다. 차오르는 막대는 "진행 중"으로 읽혀 반대 뜻이 된다.
- 막대는 `aria-hidden` — 같은 정보를 아래 카운트다운 텍스트가 이미 말한다.

### 남은 시간을 어떻게 알리나

**표기**: `4분 30초` → 60초 미만은 `59초`. 콜론(`4:30`)을 쓰지 않는다 —
`-`·`N/A`를 안 쓰는 이유와 같다(기호 대신 말). 숫자는 폭이 흔들리지 않게
`tabular-nums`를 쓴다.

**단계 변화 — 색만으로 하지 않는다:**

| 남은 시간 | 표현 |
| --- | --- |
| 4분 30초 – 1분 | 기본 텍스트, 막대 기본색 |
| 60초 미만 | 시간 텍스트가 `suspect` 색 + **굵게**, 그리고 문장 한 줄 추가 — *"1분 안에 인증하지 않으면 처음부터 다시 해야 합니다."* |

굵기와 문장을 함께 바꾸는 이유는 **색만으로 전달하지 않는다**는 규칙이다. 60초는
상태 변화인데 색만 바꾸면 색각 이상 사용자에게는 아무 일도 안 일어난 것이다.

**접근성 — 매초 읽히면 안 된다.**

- 카운트다운 숫자는 `aria-hidden="true"`. 매초 바뀌는 노드를 라이브 리전에 두면
  스크린리더가 4분 30초 동안 **270번** 말하고, 그 사이 다른 어떤 것도 들리지 않는다.
- 시각적으로 숨긴 `<span role="status" aria-live="polite">`를 따로 두고 **30초 간격**으로만
  갱신한다: *"남은 시간 4분"*, *"남은 시간 3분 30초"*.
- 마지막 1분은 **10초 간격**: *"남은 시간 30초"* … 여기서는 급한 게 실제 정보다.
- `role="timer"`는 쓰지 않는다 — 지원이 고르지 않다. `role="status"` + 수동 갱신이
  읽히는 빈도를 우리가 통제할 수 있다.

### 취소와 시간 초과가 가는 곳은 같다

둘 다 **폼으로 돌아가고 입력값을 지우지 않는다.**

- 5개 필드를 다시 채우게 하는 건 벌이다. 시간 초과는 사용자 잘못이 아니라 제한이고,
  취소는 사용자가 명시적으로 고른 것이다.
- **대시보드로 튕기지 않는다.** 여기 온 이유는 실 데이터를 보려는 것이고, 실패했다고
  그 의도를 대신 취소해 주지 않는다. 나가는 건 머리글의 `대시보드로 돌아가기`로 고른다.
- **1차부터 다시다.** `multiFactorInfo`가 만료되므로 "재시도" 버튼이 아니라 원래
  제출 버튼을 다시 누르는 것이 정확한 표현이다.

## 인터랙션

### 폼 검증

**제출 시 전체 검증, 그 뒤부터는 blur 시 개별 검증.** 입력 중에 빨간 글씨를 띄우지
않는다 — 생년월일 8자리는 3자리째에 이미 "틀렸다"가 되는데, 그건 틀린 게 아니라
덜 쓴 것이다.

| 필드 | 컨트롤 | 규칙 | 에러 카피 |
| --- | --- | --- | --- |
| 이름 | `text`, `autoComplete="name"` | 공백 트림 후 비어 있지 않음 | 이름을 입력해 주세요. |
| 생년월일 | `text` `inputMode="numeric"` `maxLength=8`, `autoComplete="bday"` | 숫자 8자리 | 생년월일을 8자리 숫자로 입력해 주세요. 예: 19900101 |
| 휴대폰 | `tel` `inputMode="numeric"` `maxLength=11` | `010` + 숫자 11자리 | 휴대폰 번호를 하이픈 없이 11자리로 입력해 주세요. 예: 01012345678 |
| 통신사 | `<select>` (placeholder `선택`) | 선택됨 | 통신사를 선택해 주세요. |
| 판정 기준 | `<fieldset>` + 라디오 2개 | 선택됨 | 판정 기준으로 쓸 성별을 선택해 주세요. |

컨트롤 근거:

- **생년월일은 `<input type="date">`가 아니다.** API가 `YYYYMMDD` 문자열을 받고,
  네이티브 피커로 1990년에 가려면 캘린더를 수십 번 넘겨야 한다. 8자리 타이핑이 빠르고
  `inputMode="numeric"`이 모바일 숫자 키패드를 띄운다.
- **휴대폰에 자동 하이픈을 넣지 않는다.** 커서가 튀고 붙여넣기가 깨진다.
  API도 하이픈 없는 값을 받는다. 형식은 placeholder와 에러 카피가 말한다.
- **통신사는 `<select>`** — 앱 규약이 선택 컨트롤을 `<select>`로 정했고 모바일에서
  OS 피커가 뜬다. 값은 `0`=SKT `1`=KT `2`=LG U+ (probe가 확인한 매핑).
  **번호를 화면에 노출하지 않는다.**
- **성별은 라디오** — 선택지가 2개면 펼치는 동작이 순수 비용이다. 대시보드의 세그먼티드
  버튼을 재사용하지 않는 이유: 그건 *이미 고른 값을 바꾸는* 컨트롤이라 항상 하나가
  눌려 있고, 폼에서는 **아직 안 고른 상태**가 표현돼야 한다.
- **라벨은 `판정 기준`** — 대시보드가 쓰던 라벨을 그대로 가져온다. 이 값은 신원이 아니라
  판정에 쓰는 기준이고, 프로필 설정처럼 보이면 왜 여기 있는지 설명되지 않는다.

**접근성**: 각 필드는 `<label htmlFor>`로 연결한다. 에러가 있으면 `aria-invalid="true"` +
`aria-describedby`가 에러 노드를 가리킨다. 도움말이 함께 있는 필드는
`aria-describedby="help-sex error-sex"`처럼 **둘 다** 나열한다 — 에러가 도움말을
대체하지 않는다. **에러 노드는 항상 DOM에 두고 내용만 채운다** (노드가 생겼다 사라지면
`aria-describedby` 참조가 끊긴다). 제출 실패 시 **첫 번째 에러 필드로 포커스**를 옮긴다.

### 포커스 관리

- 폼 → 대기: 제출 버튼이 DOM에서 사라져 포커스가 `<body>`로 떨어진다. 대기 카드 제목
  (`<h2 tabIndex={-1}>`)으로 옮기고, 카드를 `role="status" aria-live="polite"`로 감싸
  전환 자체가 한 번 읽히게 한다.
- 대기 → 폼(취소·초과·실패): **첫 필드가 아니라 안내 배너에 포커스.** 왜 돌아왔는지
  먼저 알아야 한다.

### 폼 전체 에러

폼 위, 제목 아래 카드 안 배너. `role="alert"`. **토스트가 아니다** (앱 규약).

### 성공

2차 응답을 Query 캐시(`checkupKeys.history()`)에 넣고 `/`로 이동한다.
**성공 화면을 만들지 않는다** — 사용자가 원한 건 결과지 축하가 아니다.
대시보드 부제에서 `예시 데이터`가 사라지는 것이 성공의 표시다.

| 대기 본문 | 토스 앱에 인증 요청을 보냈습니다. 앱에서 인증을 마친 뒤 아래 버튼을 눌러 주세요. | 무엇이 일어났는지 + 무엇을 할지 |
| 타이머 라벨 | 남은 시간 | — |
| 타이머 값 | 4분 30초 / 59초 | 콜론 표기를 쓰지 않는다 |
| 60초 경고 | 1분 안에 인증하지 않으면 처음부터 다시 해야 합니다. | 결과를 미리 알린다 |
| 2차 버튼 | 인증을 완료했습니다 | 사용자가 한 일을 서술한다. "확인"은 무엇을 확인하는지 모호하다 |
| 2차 진행 중 | 결과를 불러오는 중… | — |
| 취소 버튼 | 취소 | — |
| 스크린리더 갱신 | 남은 시간 3분 30초 | 30초 간격, 마지막 1분은 10초 |
| 시간 초과 | 인증 시간 4분 30초가 지났습니다. 입력한 내용은 그대로 두었으니 다시 요청해 주세요. | 무엇이 + 어떻게 + **잃은 게 없다는 것** |
| 인증 실패 | 인증을 완료하지 못했습니다. 토스 앱에서 인증을 마쳤는지 확인하고 다시 요청해 주세요. | 원인 + 다음 행동 |
| 키 없음 | 검진 조회 서비스가 설정되지 않았습니다. 예시 데이터로 화면을 볼 수 있습니다. | 배포본에 키가 없을 때. 평가자가 만날 수 있는 상태다 |

에러는 전부 **무엇이 일어났는지 + 어떻게 할지**다. 스택 트레이스·HTTP 코드·API 원문
메시지를 노출하지 않는다.

## 미해결

- **인증 실패 원인을 나누지 못한다.** 사용자 거절·입력 불일치·서버 오류를 구분하려면
  실패 응답의 형태를 알아야 하는데, probe는 **성공 경로만** 캡처했다. 지금은 문구 하나로
  합쳐 두고, 실제 실패 응답을 본 뒤에 쪼갠다. **추측으로 분기하지 않는다.**
- **2차 요청을 폴링으로 바꿀 수 있는지.** 인증 완료 전 호출의 동작이 확인되면
  버튼 없이 자동으로 넘어가는 편이 낫다. 확인 전까지는 버튼이다.

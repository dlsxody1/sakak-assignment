# 건강검진 대시보드

CANDiY API를 연동해 건강검진 결과를 시각화하는 SPA.
6회차(2020–2025) × 검사항목 21개를 판정해 보여준다.

## 실행

```bash
pnpm install
pnpm dev
```

## 스크립트

| 명령 | 설명 |
| --- | --- |
| `pnpm dev` | 개발 서버 |
| `pnpm build` | 타입체크 + 프로덕션 빌드 |
| `pnpm test` | 테스트 |
| `pnpm lint` | oxlint |

## 기술 스택

TypeScript / React 19 / Vite / TanStack Router / TanStack Query / Tailwind CSS v4 /
ApexCharts / react-icons / zustand / Vitest

## 판정은 5단계다

요구사항은 초록·주황·빨강 3색이지만 **데이터가 3색으로 나뉘지 않는다.**
API의 `refType` 4종에 실제 값을 맞춰보면 두 경우가 더 생긴다.

| 판정 | 언제 |
| --- | --- |
| `normalA` `normalB` `suspect` | 값이 해당 구간에 걸렸다 |
| `unmeasured` | 측정값이 없다 (빈 문자열) |
| `undetermined` | 어느 구간에도 안 걸렸거나, 기준을 해석하지 못했다 |

미측정과 판정불가를 "정상"으로 뭉개지 않는다. 건강 데이터에서 *모르는 것*을
*괜찮은 것*으로 표시하는 건 사실과 다르다.

fixture 6회차를 판정하면 **정상 70 · 판정불가 30 · 미측정 14 · 질환의심 12** 가 나온다.
판정불가 30건 중 24건은 신장·체중·시력·청력으로, **기준 자체가 제공되지 않는** 항목이다.
화면에서는 이 둘을 구분한다 — 전자는 "기준 없음"으로 수치만, 후자는 판정불가 배지를 단다.

## 기준 문자열 파서

`referenceList`가 판정 기준을 자연어로 준다. 같은 `/`가 항목마다 다른 뜻이라
범용 처리를 하면 반드시 틀린다.

| `/`의 의미 | 항목 | 예 |
| --- | --- | --- |
| 성별 분기 | 허리둘레·혈색소·감마지티피 | `남: 13-16.5 / 여: 12-15.5` |
| 수축기/이완기 | 혈압 | `140이상 또는 /90이상` |
| 구간 합집합 | 체질량지수 | `18.5미만/25~29.9` |
| 좌/우 | 시력·청력 | `1.2/1.0` (기준 없음) |

파서는 문자열을 중간표현(`Criterion`)으로 옮기고, 해석하지 못하면 `null`을 준다.
**예외 테이블을 두지 않는다** — 기준을 추측해서 판정하느니 판정불가로 남긴다.

### 회귀 기준

`lib/judge.test.ts`가 고정한다. 이 값들이 바뀌면 파서가 망가진 것이다.

| 케이스 | 기대 | 왜 |
| --- | --- | --- |
| 2022 `LDL=148` | 판정불가 | 정상B `130-139`와 질환의심 `160이상` **사이 공백** |
| 2024 `Hb=16.8` | 판정불가 | 남 정상A 상한 `16.5` 초과, 어느 구간에도 없음 |
| 2025 `BP=142/88` | 질환의심 | `140이상 또는 /90이상`의 OR에서 **수축기만** 걸림 |
| 2021·2023 지질 4종 | 미측정 | 격년 검사라 통째로 결측 |

**판정은 나쁜 쪽부터 매칭한다.** 혈압 `142/88`은 정상B(`120-139 또는 /80-89`)의
이완기 조건과 질환의심의 수축기 조건에 동시에 걸린다. OR 기준이 겹치는 이상
답은 나쁜 쪽이다.

## 화면

모바일 우선. 한 항목 = 한 줄이라 좁은 화면에서 가로 스크롤이 없고,
넓은 화면에서는 요약·추이·이력을 왼쪽, 항목 목록을 오른쪽에 나눈다.

**≥1024px에서 페이지 자체는 스크롤하지 않는다.** 대시보드는 훑는 화면인데 전체가
수천 픽셀이면 훑기가 성립하지 않는다. 넘치는 것은 검사 항목 목록 안에서만 스크롤하고,
요약·추이·이력은 항상 보인다. 검사 묶음은 접히되 **질환의심이 있는 묶음만 기본 펼침**이며,
접힌 묶음도 머리글에 질환의심 수를 달아 접기가 정보를 숨기지 않게 한다.

- **상태 요약** — 최신 회차 판정 분포를 비율 막대로. 그 아래 주의가 필요한 항목.
  머리에 **남/여 전환**이 있다 — API가 성별을 주지 않는데 허리둘레·혈색소·감마지티피는
  기준이 성별로 갈려서, 잘못된 기준으로 조용히 판정하느니 무엇을 기준으로 봤는지 드러낸다
- **추이 차트** — 배경에 기준 구간을 띠로 깔아 선이 어느 띠에 있는지가 곧 판정이다.
  띠를 ApexCharts `annotations`로 그리지 않는다 — DOM 순서상 시리즈 뒤에 와서 **선을 덮는다.**
  차트 뒤에 별도 배경 레이어로 깔고 그 위에 투명한 차트를 얹는다.
  띠 위에 라벨도 얹지 않는다. 범례가 기준 문자열과 함께 말한다.
  결측 회차는 선을 끊는다 — 이으면 받지 않은 검사를 받은 것처럼 보인다
- **항목 선택** — 17개를 칩으로 늘어놓으면 가로로 밀어야 해서 `<select>`를 쓴다.
  **가로 스크롤을 만들지 않는다** — 잘린 항목은 사용자에게 없는 항목이다
- **항목 목록** — 탭하면 판정 기준 원문과 6회차 값이 펼쳐진다

**색만으로 판정을 전달하지 않는다.** 5단계는 색 + 라벨 + 형태(`● ◐ ▲ ○ ?`)로
중복 부호화한다. 적록색맹 사용자가 정상과 위험을 구분 못 하면 치명적이다.

## 데이터

**기본은 예시 데이터다.** 링크를 열면 인증 없이 바로 대시보드가 보인다
([`shared/api/__fixtures__`](src/shared/api/__fixtures__)). 부제에 `예시 데이터`가 붙어
지금 보는 게 실제 기록이 아님을 밝힌다.

실 데이터는 `내 검진 결과 불러오기` → [`/login`](src/pages/auth)에서
2단계 인증(토스, 4분 30초)을 거친다. 인증을 안 해도 화면이 온전히 보이는 이유는
실 데이터와 fixture가 **같은 정규화 경로**를 지나기 때문이다.

**실패해도 폴백 코드가 없다.** 2차 응답이 성공하면 Query 캐시
(`checkupKeys.history()`)를 덮어쓰고, 실패하면 안 덮는다 — 덮지 않는 것이 곧 폴백이다.
`try/catch`도 `?? fixture`도 필요 없다.

응답에서 주의할 것:

- 스칼라가 전부 string이고 **빈 문자열이 결측**이다 (`caseType`만 number)
- **정렬 방향이 섞여 있다** — `overviewList`는 오래된 순, `resultList`는 최신순.
  정규화에서 방향을 고정한다
- `resultList`는 날짜당 일반·구강 2건. 안정 정렬이라 순서가 입력에 좌우되므로
  일반을 먼저 두도록 명시한다

## 2단계 인증과 프록시

**CANDiY는 CORS 헤더를 주지 않는다.** 직접 확인했다 —
`OPTIONS /v1/nhis/checkup`이 403을 주고 `access-control-*` 헤더가 하나도 없다.
브라우저에서 직접 부를 수 없으므로 서버를 거치는 것 외에 방법이 없다.

그래서 [`api/checkup.ts`](api/checkup.ts) 서버리스 함수가 프록시한다.
**이게 API 키 노출 문제까지 같이 해결한다** — `API_KEY`에 `VITE_` 접두사가 없어서
번들에 들어가지 않는다. 제약이 강요한 우회가 보안 결정과 같은 답이었다.

```
폼 → 1차 요청 (inquiryType:"0", loginTypeLevel:"8"=토스)
   → 응답의 .data 통째로 보관
   → 사용자가 토스 앱에서 인증 (4분 30초)
   → 2차 요청 (isContinue:"1" + multiFactorInfo:<1차 .data>)
   → Query 캐시에 주입 → 대시보드
```

- **`multiFactorInfo`는 1차 응답의 `.data`를 통째로** 넣는다. 일부만 골라 넣으면 실패한다.
  프록시도 바디를 파싱하지 않고 원문을 그대로 넘긴다.
- **4분 30초를 함수가 붙잡지 않는다.** 대기는 브라우저가 하고 함수는 요청 1건씩
  짧게 끝난다. 서버리스에서 4분 30초를 잡고 있으면 실행 제한에 걸린다.
- **폴링하지 않는다.** 사용자가 `인증을 완료했습니다`를 누를 때 2차를 1회 보낸다.
  검증된 출처([`probe-candiy.sh`](scripts/probe-candiy.sh))가 그 형태이고, 인증 완료 전
  호출의 동작은 확인되지 않았다 — 모르는 채로 반복 호출하면 인증 세션을 스스로 깨뜨릴 수 있다.
- 프록시는 인증 없이 공개되므로 **필수 필드를 서버에서도 검증한다.**
  안 하면 남의 키로 임의 요청을 대신 쏴주는 오픈 프록시가 된다.

**성별은 인증 폼에서 받는다.** API 응답에 성별이 없는데 허리둘레·혈색소·감마지티피는
기준이 성별로 갈린다. 예시 데이터는 남성 기준으로 판정하고, 성별이 판정을 어떻게 바꾸는지는
[`sex.test.ts`](src/entities/health-reference/lib/sex.test.ts)가 고정한다
(혈색소 12.5는 남 정상B, 여 정상A).

## 배포

**[배포된 대시보드](https://dashboard-alpha-ten-71.vercel.app)** — 인증 없이 바로 보인다.

Root Directory를 **`dashboard`**로 잡는다. 저장소 루트에 `package.json`도 lockfile도
없고(패키지 2개가 각각 갖는다), `vercel.json`이 여기 있다. 루트로 잡으면 프레임워크
감지도 SPA rewrite도 실패한다.

| 항목 | 값 |
| --- | --- |
| Root Directory | `dashboard` |
| Framework | Vite (자동 감지) |
| 환경변수 | `API_KEY` — **`VITE_` 접두사를 붙이지 않는다** |

접두사가 없으면 Vite가 번들에 주입하지 않는다. 붙이는 순간 키가 공개된다.
저장 후 **재배포해야** 적용된다 (기존 배포에 소급되지 않는다).

**키가 없어도 배포는 동작한다.** 대시보드가 예시 데이터로 열리고, 인증만
`검진 조회 서비스가 설정되지 않았습니다`로 답한다.

`api/`는 [`tsconfig.node.json`](tsconfig.node.json)의 `include`에 넣었다.
안 넣으면 `tsc -b`가 함수를 건너뛰어 **빌드는 통과하고 런타임에 터진다.**

## 구조

FSD. 규칙의 단일 출처는 [`shared/config/fsd.ts`](src/shared/config/fsd.ts)이고
[`fsd-boundaries.test.ts`](src/shared/config/fsd-boundaries.test.ts)가 강제한다.

```
entities/health-reference  판정 도메인(순수 함수) + 판정 배지·색 체계
entities/checkup           응답 정규화, Query 훅, 검사 항목 행·상세·이력 표현
entities/user              성별 세션 (zustand)
features/measurement-detail  항목·묶음을 펼쳐 판정 근거를 확인하는 행위
features/trend-explorer      항목을 골라 추이를 보는 행위 (기준 띠 계산 포함)
features/checkup-inquiry     2단계 인증으로 검진 결과를 조회하는 행위
widgets/checkup-overview     엔티티·피처 조립 + 요약 집계
pages/dashboard              위젯 조립
pages/auth                   인증 화면 조립
```

`health-reference`가 `checkup`을 모르고 그 반대도 마찬가지다 —
같은 레이어의 슬라이스끼리는 참조하지 않고 위젯에서 합쳐진다.
`Measurement<TJudgement>`가 제네릭인 것도 이 때문이다: `checkup`은 판정 타입을
import할 수 없어서, 실제 타입으로 좁히는 건 둘이 만나는 위젯의 몫이다.

**경계 테스트가 통과해도 배치가 맞는 건 아니다.** 테스트는 잘못된 방향의 import만
잡지, 전부 위젯에 몰아넣은 것은 못 잡는다. 도메인 개념 하나를 그리면 `entities/ui`,
사용자 행위면 `features`, 조립이면 `widgets`다.

계산은 컴포넌트에 두지 않는다. 날짜별 그룹핑·판정 집계·축 눈금 계산은 전부 `lib/`의
순수 함수이고 각각 테스트가 있다 — 렌더링 없이 입출력만으로 검증된다.

## 아직 안 한 것

- **인증 실패 원인을 나누지 못한다.** 사용자 거절·입력 불일치·서버 오류를 구분하려면
  실패 응답의 형태를 알아야 하는데 probe가 성공 경로만 캡처했다. 문구 하나로 합쳐 두고
  실제 실패 응답을 본 뒤 쪼갠다 — 추측으로 분기하면 모르는 코드에서 틀린 안내를 한다
- **컴포넌트 테스트가 없다.** `@testing-library/react`가 없고 순수 함수와 경계만 검증한다.
  폼 검증·타이머는 `lib/`의 순수 함수로 빼서 테스트를 붙였다
- ApexCharts가 번들에 약 970 kB를 더한다. 라우트 분할이 필요해지면 그때 나눈다

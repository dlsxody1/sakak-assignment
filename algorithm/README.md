# 개미수열 (Look and Say Sequence)

양의 정수 n(3 < n < 100)이 주어질 때, n번째 항 Ln의 가운데 두 자리 수를 반환한다.

## 실행

```bash
pnpm install
pnpm test
```

## 막혔던 부분

### 1. "묶는다"를 잘못 읽었습니다.

2개 이상 붙어 있을 때만 묶음이라고 이해했습니다. 그러면 21처럼 같은 숫자가 이웃하지 않은 항에는 묶음이 없고, 개수가 0이 되어야 하지 않나 하는 데서 멈췄습니다.

묶는다는 건 모든 숫자를 빠짐없이 구역으로 나눈다는 뜻이었습니다. 혼자 있는 숫자도 1개짜리 묶음입니다. 21은 묶음이 없는 게 아니라 2 하나와 1 하나, 두 개라서 "2가 1개, 1이 1개"가 되고, 그래서 1211입니다.

### 2. 홀수 길이일 때 가운데를 정할 수 없습니다.

문제는 가운데 두 자리를 요구하는데 홀수 길이일 때의 규칙이 없습니다. 길이가 5라면 가운데를 왼쪽으로 잡을지 오른쪽으로 잡을지 근거가 없습니다. 이건 아래에서 다시 다룹니다.

## 풀이 설명

함수를 둘로 나눴습니다. next는 한 항에서 다음 항을 만드는 일만 하고, solve는 그걸 n-1번 돌린 뒤 가운데를 잘라내는 일만 합니다. 수열을 만드는 일과 자리를 고르는 일은 관심사가 다릅니다. 붙여두면 가운데가 왜 저기냐를 확인할 때 수열 생성 코드까지 같이 읽어야 합니다.

### next — 한 번 읽고 끝낸다

이웃한 같은 숫자를 묶어서 개수 다음에 숫자를 적으면 됩니다. 포인터 하나를 앞으로만 밀면서 같은 숫자가 이어지는 동안 세면 되고, 되돌아갈 일이 없어서 문자열을 한 번만 지납니다.

```ts
while (i < s.length) {
  const current = s[i]; // 지금 세는 숫자
  let count = 0;
  while (i < s.length && s[i] === current) {
    count++;
    i++;
  }
  result += count + current; // 개수 먼저, 숫자 나중
}
```

바깥 while과 안쪽 while이 겹쳐 있어서 O(n²)처럼 보입니다. 그런데 i를 증가시키는 곳이 안쪽 루프 한 군데뿐입니다. 바깥 루프는 i를 건드리지 않으니 두 루프를 합쳐도 i는 0에서 s.length까지 딱 한 번 올라갑니다. 곱이 아니라 합이라 O(n)입니다.

### solve — 가운데를 어떻게 정했나

s.length / 2를 Math.floor 없이 인덱스로 쓰면 길이가 홀수일 때 깨집니다. 그런데 L2부터는 항상 짝수라 깨지지 않습니다.

근거는 next의 출력 형태에 있습니다. 결과가 개수와 숫자 쌍의 나열이니 쌍이 몇 개든 길이는 2의 배수입니다. 유일한 홀수 항은 길이 1인 L1인데, n > 3이라는 제약이 이걸 범위 밖으로 밀어냅니다. 홀수 길이는 들어올 수 없습니다.

L2부터 전부 짝수라고 가정했습니다.

그래서 위에서 걸렸던 홀수면 어느 쪽이 가운데냐는 정할 필요가 없는 문제였습니다. 규칙을 임의로 고르는 대신, 그런 입력이 아예 안 들어온다는 걸 보이는 쪽을 택했습니다.

### 범위 검사

solve는 3 < n < 100을 벗어나면 RangeError를 던집니다. 조건 밖의 값에 그럴듯한 숫자를 돌려주면 호출한 쪽이 틀린 걸 모르고 씁니다.

Number.isInteger로 1.5와 NaN을 같이 막았습니다. NaN은 모든 비교가 false라서 크기 비교만으로는 그냥 통과해버립니다.

## 복잡도 분석

### 비용은 루프가 아니라 문자열 크기에서 나온다

next 하나만 보면 O(n)이라 싸 보입니다. 문제는 그 n이 매번 커진다는 데 있습니다. 실제로 길이를 재봤습니다.

| n   | 길이       |
| --- | ---------- |
| 10  | 20         |
| 20  | 302        |
| 30  | 4,462      |
| 40  | 63,138     |
| 50  | 894,810    |
| 60  | 12,680,852 |
| 62  | 21,549,544 |

이웃한 두 항의 비를 내보면 **1.3036** 근처로 수렴합니다. 즉 항 하나 늘어날 때마다 길이가 1.3배씩 붙습니다.

### 그래서

- 시간 O(1.3ⁿ). next를 n-1번 부르고 각 단계 길이가 1.3배씩 늘어납니다. 등비수열의 합은 마지막 항이 지배하므로 총합도 같은 규모입니다.
- 공간 O(1.3ⁿ). 매 단계 새 문자열을 만들고 이전 것을 버립니다. 피크는 이전 항과 결과가 함께 살아 있는 순간이라 마지막 항 길이의 약 2배입니다.

n이 100 미만이라 형식적으로는 O(1)이라고 쓸 수도 있습니다. 하지만 아래처럼 실제로 안 돌아가는 구간이 있어서 그 표현은 실상을 가립니다.

n=99는 이 방식으로 도달 불가입니다.

### 왜 우회가 안 되나

가운데 두 자리만 필요한데 항 전체를 만드는 게 낭비로 보입니다. 실제로 두 가지를 시도해봤습니다.

가운데에서 거꾸로 올라가기. Ln의 k번째 쌍은 Ln₋₁의 k번째 묶음에서 나옵니다. 그런데 묶음 길이가 제각각입니다. 1은 1글자, 11은 2글자, 222는 3글자라서 k번째 묶음이 어느 위치에서 시작하는지 알려면 앞의 묶음을 전부 세야 합니다. 결국 전체가 필요합니다.

길이만 미리 구하기. 목표 위치를 알려면 전체 길이가 있어야 합니다. Ln의 길이는 Ln₋₁의 묶음 개수 곱하기 2인데, 묶음 개수는 그 항의 내용에 달려 있습니다. 내용을 알려면 만들어야 하고, 만들 수 없어서 시작한 문제라 제자리로 돌아옵니다.

두 번 다 같은 자리에서 막혔습니다. 개미수열은 가운데가 앞뒤 전체에 의존해서 부분만 계산할 수 없습니다.

과제 예시(n=5, n=8)와 테스트 범위에서는 지금 구현이 즉시 끝나고 읽기도 쉽습니다. 그래서 동작 상한을 문서에 적어두는 쪽을 택했습니다.

## 소감

알고리즘 문제를 너무 오랜만에 풀어서 쉽지 않았습니다. 규칙부터 잘못 본 바람에 실수도 했지만, 문제를 정확히 읽는게 절반이구나 싶었고 제 코드가 잘못된걸까 싶었는데 길이를 재보니 항 하나마다 1.3배씩 늘어나고 있었고, 그냥 최적화로는 풀리지 않았습니다.
AI한테 물어보니 Cosmological Theorem 이라는게 있었고,요약하면 이렇습니다. 개미수열은 충분히 여러 번 읽고 나면, 어떤 항이든 서로 절대 섞이지 않는 92개의 조각으로 쪼개집니다. 각 조각은 한 번 읽으면 정해진 다른 조각들로만 바뀌고, 92개 밖의 새로운 조각은 생기지 않습니다. 그래서 문자열을 통째로 들고 있을 필요 없이 조각이 각각 몇 개인지만 세면 됩니다. 한 단계 나아가는 일은 92 x 92 행렬을 한 번 곱하는 일이 되고, 길이는 조각 개수와 조각 길이를 곱해서 더하면 나옵니다. 제가 실측한 1.3036도 이 행렬에서 나오는 값이라고 합니다.
여기까진 읽어서 알겠는데.. 그래서 가운데 수는 어떻게 수하는거지? 조각이 몇 개인지만 세면 순서정보가 사라지는거 아닌가? 라는 생각이 들었고, 앞에서 부터 조각 길이를 더해가면서 목표 위치가 들어있는 조각을 찾고, 그 조각만 다시 펼치는 식이겠거니 짐작했지만 확신이 서지않았고,
그것을 코드로 구현하기가 참 어려웠습니다. 그런데 n=99 까지 되는 답을 적어볼까 아다가, 이해하지 못한 코드는 나중에 설명도 드리기 어려울 것 같아, 지금 구현이 어디까지 동작하고 왜 거기서 멈추는지를 직접 재서 적는 쪽을 택했습니다.
마지막으로 이런 기회를 주신 (주)사각 관계자분들께 감사드립니다. 덕분에 오랜만에 문제 하나를 붙잡고 오래 고민해봤습니다. 못 푼 부분까지 포함해서 좋은 경험이었습니다.
